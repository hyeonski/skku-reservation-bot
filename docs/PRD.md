# 교내 공간 예약 에이전트 — PRD 요약

> 최종 수정: 2026-05-15
> 본 문서는 팀 통합 PRD를 읽고 이해한 내용을 정리한 것이다.

---

## 1. 문제 정의

성균관대 GLS 포털의 공간 예약은 다음과 같은 누적된 불편을 가진다.

1. **탐색 비용**: 건물별로 일일이 시간표를 열어 빈 공간을 눈으로 찾아야 함. 교내 전체를 한눈에 비교 불가.
2. **예약 반려 리스크**: 학과 전용 강의실 정보가 예약 시점에 노출되지 않아, 신청 후 행정실 컨펌을 기다려야 반려 여부를 안다. 같은 강의실도 시기에 따라 결과가 달라짐.
3. **진입 장벽**: 첫 사용자는 메뉴 경로(홈페이지 → GLS → 공간대여신청)부터 어렵다.
4. **반복 입력 부담**: 정기 모임은 매주 동일 폼(행사구분/주관단체/행사명/사용목적 등)을 반복 입력.
5. **공간 쏠림**: 통합된 뷰가 없어 특정 공간으로 수요가 집중.
6. **공간예약승인서 제출**: 승인 후 출력→경비실 방문 제출이라는 물리적 번거로움.

### 타겟
- **핵심**: 학생회 간부, 동아리 임원 등 공간 예약 담당자 (예약은 본업이 아닌 잡무).
- **확장**: 연구실 교직원, 프로젝트 팀 등 성균관대 구성원 전체.

## 2. 솔루션

자연어 대화 한 번으로 탐색·반려리스크·진입장벽·반복 입력을 모두 해소하는 **크롬 확장 기반 에이전트**. 기존 포털을 수정하지 않고 위에 지능형 레이어를 얹어 학교 협조 없이 즉시 적용 가능.

### Phase 로드맵

| Phase | 내용 |
|---|---|
| **1 — 핵심 파이프라인 (MVP)** | 자연어 예약 요청, 빈 공간 자동 탐색(강한/약한 필터), 인원 기반 최적 할당, 신청서 자동 작성 |
| **2 — 개인화** | 예약 이력 저장, 선호(공간/시간/인원) 학습 |
| **3 — 리마인드** | 정기 일정 등록, 알림→사용자 확인 후 예약, weight decay 기반 알림 해제 |
| **4 — 스케줄링** | 사용자 확인 없는 자동 반복 예약, 실패 시 알림/대안 |
| **5 — 영역 확대** | 도서관 스터디룸, 열람실 좌석 등 |

- **강한 필터**: 사용자가 명시한 건물/공간 지정 탐색
- **약한 필터**: 이력 기반 선호 공간 우선, 그 외 교내 전체 스캔 (쏠림 방지)
- Nice-to-have: 학과 전용 등 메타데이터를 축적한 강의실 DB

## 3. 사용자 플로우

### 시나리오 A — 일반 예약 (Phase 1)
1. 확장 아이콘 클릭 후 Chrome side panel로 진입
2. 자연어 입력 ("다음 주 화요일 6시 20명 학생회 회의", "내일 18시부터 20시까지 330112 예약")
3. 에이전트가 조건 파싱 → 인원 조건 기반 후보 탐색
4. 사용자 확인 + 행사 메타(행사구분/주관단체/행사명/사용목적) 입력
5. 포털 폼 자동 작성, 필요 시 미리보기 후 신청 → 완료 알림
- 세션 없으면 3단계 전에 로그인 페이지 안내
- 성균관대 구성원은 공간을 건물번호+공간코드/호실 번호로 부르는 경우가 많다(예: "26312에서 수업", "330112 예약"). 자연어 파서는 건물명뿐 아니라 이런 숫자형 공간 지정도 우선 인식해야 한다.
- 추천 카드·확인 요약·완료 메시지에는 건물명과 공간명만이 아니라 번호도 함께 표시한다. 예: `제2공학관(26동) XXX강의실(26312)`. 한 건물이 여러 동으로 나뉘거나 사용자가 숫자 코드로 기억하는 경우가 많으므로, 번호는 보조 정보가 아니라 식별 정보로 취급한다.

### 시나리오 B — 정기 예약 (Phase 3~4)
1. 정기 일정 등록 ("매주 화요일 6시 학생회 회의")
2. [Phase 3] 예약 시점 알림 → 사용자 확인 후 진행
3. [Phase 4] 자동 실행, 실패 시 대안 제시
4. 앱 초기화면에 현재 정기 예약 강의실/시간 표시

### 시나리오 C — 앱(향후)
스마트폰 앱에서 SKKU 로그인 후 채팅으로 동일 플로우.

### 엣지 케이스
- 세션 만료, 빈 공간 없음, 선점 race, **반려 감지 및 재신청**, 조건 불완전 시 되묻기, 포털 UI 변경, 동일 시간대 이중 예약, 24h 가능 공간 vs 제한 공간, 정기예약 선점 시점, 정기예약 형평성 이슈
- **반려 플로우**: 신청 후 일정 시간 뒤 "승인 상태 확인할까요?" → 포그라운드에서 확인 → 반려 시 사유 안내 + 대안 탐색 → 반려 이력은 추천 제외에 활용

## 4. 기술 아키텍처

```
[서버]
├── LLM API 프록시
├── 사용자 데이터 (예약 이력, 신청 정보, 리마인더)
├── 반복 패턴 기반 리마인더 생성

[크롬 확장]
├── Side panel UI (자연어 입출력)
├── Content Script (포털 DOM 조작 / 폼 자동 작성)
├── Background SW (서버 알림 수신, 상태 관리)
```

- **인증 정보는 서버에 저장 안 함**. 포털 조작은 사용자 브라우저에서, 세션은 로컬에만.
- 서버는 LLM 파싱, 대화·신청 이력 mirror, 공간 후보 조회, 반복 패턴 기반 리마인더 생성에 한정.

### 스택 (현재 구현)
- LLM: DeepSeek-Chat (`deepseek-chat`, OpenAI 호환 API)
- 서버: TypeScript + Fastify + Prisma + MySQL
- 자동화: Chrome Extension API + background service worker + content script + main-world bridge
- 알림: `chrome.notifications` (예약 완료 시점)
- 저장: MySQL(`Client`/`Conversation`/`Space`/`Reminder`) + `chrome.storage.local/session`

### 현재 구현 메모
- 진입점은 Chrome side panel 기준이며, 포털 내 플로팅 버튼은 아직 구현되지 않음
- 후보 공간은 `/spaces`에서 인원 기준으로 추린 뒤 GLS에서 직렬 검증
- 과거 완료 대화의 신청 정보를 추천·재사용하는 개인화 일부가 구현됨
- 같은 요일·시간·단체·행사 패턴이 반복되면 다음 예약을 제안하는 리마인더 일부가 구현됨
- 반려 감지·재신청과 사용자 확인 없는 자동 반복 실행은 아직 구현 범위 밖

### 주요 챌린지
- **P1**: DOM 자동화 안정성 (드롭다운/달력), 세션 감지, LLM 파싱 정확도(자연어→폼 선택지 매핑), 외부 예약 시스템 구조 통합, race condition
- **P2**: 개인화 수준 경계 (추론 vs 명시적 확인)
- **P3**: 알림 직관성, 알림→예약 자연스러운 연결, 폴백
- **P4**: 자동 실행 UX (포그라운드 기본, 불편 시 백그라운드 검토), 브라우저 미실행 시 폴백

## 5. 제약·리스크

### 제약
- 포털 공개 API 없음 → DOM 의존 → UI 변경 취약
- Chrome/Chromium 한정
- LLM API 비용, 서버 운영 비용 (학기 예산 제한)
- 학교 이용약관상 자동화 허용 여부 불확실
- 보안: 로그인 세션 활용에 따른 경각심
- 책임 소재: 에이전트 오작동으로 잘못된 예약 발생 시

### 핵심 리스크 대응
- DOM 셀렉터를 설정 파일로 분리해 빠른 대응
- 최종 신청 전 사용자에게 요약 보여주고 **명시적 확인 단계 필수**
- 룰 기반 처리로 LLM 호출 최소화, 호출 모니터링
- 인증 정보 서버 비저장 구조 유지
- 반려 이력 축적으로 강의실 DB 점진 구축

## 6. 성공 지표

### 정량
- 예약 소요시간: 수동 대비 **50% 이상 단축**
- 예약 성공률: **90% 이상**
- 사용자 개입(되묻기): 평균 **1회 이하**

### 정성
- 재사용 의향, 불편 지점 자유 피드백, 수동 대비 체감 편의성 (5점 척도)

### 궁극 목표
교내 학생들이 공간 예약 시 **첫 번째로 찾는 도구**가 되는 것.

### 테스트
- 학생회 5~6개 + 동아리 10개 (총 15~16개 단체), 약 2주, iterative 업데이트.

### 인앱 계측
- 서버: 요청 횟수/성공률/소요시간, 자연어↔파싱 매핑, 되묻기·대안 제시 횟수, 재사용률
- 에러: DOM 실패, 세션 만료, LLM 응답 오류
- 인앱 피드백: 예약 완료 후 👍/👎 또는 1~5점, 불만족 사유 선택지
